# 슬라이스 8 — 평가 세트 재생기 (2026-09-11)

실제 이름·경로는 여기 적지 않는다. 매핑은 로컬 전용 파일에 있다 (`ANONYMIZATION.md §5`).

```
npm run eval        # 픽스처를 다시 만들고 시나리오 10개를 재생 → data/eval/scenarios.json
```

## 무엇을 했나

`PRD.md §9` 의 시나리오 10개를 픽스처로 재생해 기대와 대조하는 스크립트 하나(`scripts/eval.mjs`)와,
`/eval` 화면(슬라이스 10)이 읽을 결과 파일(`data/eval/scenarios.json`)이다.
`observeFleet` 에 `planDirty` 인자를 열어 준 것(`src/fleet/source.mjs`)이 코드 변경의 전부다 —
**판정 규칙은 하나도 안 만들었다.** 재생은 `observeFleet` 결과를 읽고, 사유 문장은 sp-sync 가 낸 것을 그대로 싣는다.

결과 (2026-09-11 실측): **재생 9 / 일치 9 / 불일치 0 / 재생 불가 1**. 회차 하나(관찰+판정)가 356~438ms,
합계 3.6초 — `PRD.md §8` 의 "10초 이내" 안쪽이다.

## 시나리오마다 관찰을 따로 돈다

두 이유가 있었고 둘 다 PLAN 검토에서 나온 것이다.

- **시나리오 3의 `planDirty` 는 그 프로젝트의 새 파견을 전부 막는다** (R2). 4·5·10 과 한 관찰에 섞으면
  그 셋이 같이 "PLAN.md 미커밋" 사유로 떨어져 헛되이 불일치가 된다.
- **회차 소요를 잴 자리가 여기뿐이다** (R7). 관찰부터 판정까지가 한 회차이므로 시나리오마다 그 한 바퀴를
  통째로 잰다. 시나리오별 ms · 합계 · 가장 긴 회차를 내고, 10초를 넘으면 실패로 센다.

판정 시각(`now`)은 한 번 정해 모든 관찰에 같이 넘긴다 — 픽스처 시각이 상대값이라, 관찰마다 따로 재면
"턴이 묵었나"의 답이 관찰 사이에 갈릴 수 있다.

## 시나리오 3 — 사유 문장을 베끼지 않고 받아 온다

`planDirtyBlock` 은 저장소를 실제로 보고 사유를 낸다(`git status -- PLAN.md`). 문장을 스크립트에 베껴 두면
sp-sync 가 문구를 고쳤을 때 재생만 옛 문장으로 통과한다. 그렇다고 픽스처 본체를 더럽힐 수도 없다 —
재생은 읽기여야 한다.

그래서 **임시 폴더에 픽스처와 같은 계획서를 가진 git 저장소를 하나 만들어** 미커밋 상태를 실제로 만들고
탐지 함수를 그대로 부른다. 깨끗할 때 `null` 이 나오는 것도 같이 확인한다 — 탐지가 늘 켜져 있는 게 아니라
미커밋일 때만 켜진다는 뜻이다. 임시 폴더는 끝나면 지운다. `sandbox/fleet/` 은 손대지 않는다.

`hold` 코드는 `other` 로 떨어진다 — `HOLD_CODES` 는 파견 보류 사유 접두어만 담고 있고 planDirty 문장은
거기 없다. 대조는 사유 문장으로 하므로 재생에는 지장이 없다. (`발견한 것` 에 적었다.)

## 시나리오 8 — 판정 재료가 워크스페이스 상태가 아니다

R3 이 짚은 함정이다. `landCheck` 는 카드를 실제 홈에서만 읽어(`cardForWorkspace`, 주입 구멍 없음)
픽스처 카드가 안 붙는다. 실측으로 beacon/slice3 의 `state` 는 `busy`, `counts.waiting` 은 세 프로젝트
모두 0이다. 워크스페이스 상태를 대조하면 8번이 헛되이 불일치가 되고, 그걸 맞추려 픽스처나 판정 규칙을
고치면 `PRD.md §7` 을 어긴다. 그래서 **재개 갈래(`resume[].action === 'wait'`)와 `cards[]`** 로 본다.

## 시나리오 9 는 재생하지 않는다 — 지어내는 대신 수를 적는다

샌드박스에는 살아 있는 워커 세션이 없어 충돌 해소를 시도조차 하지 않는다(`src/fleet/execute.mjs` 의
`conflict`). 반입한 회차 기록으로 보여주는 데까지인데, **그 표에도 "충돌" 이 든 행이 0개다** (회차 241개
전수, 스크립트가 매번 세어 표에 적는다). 그래서 `재생 불가` 로 두고 분모에서 뺀 뒤 그 사유를 표에 남긴다.
일치율은 재생한 것만 분모다 — 어느 쪽으로도 유리하게 세지 않으려고 두 수를 그대로 낸다.

## 시나리오 5 는 PRD 예시와 상한 값이 다르다

`PRD.md §9` 는 "상한 3 설정 → 넷째 슬라이스 보류" 로 적었지만 픽스처의 beacon 은 상한 2다(둘이 이미 돌고
4번이 자격을 받아 셋째가 되는 자리). 재는 것은 같다 — **상한을 채운 뒤의 다음 슬라이스가 `cap-project` 로
보류되는가.** 픽스처를 늘리지 않는다(그러면 다른 시나리오의 표본이 같이 바뀐다). 상한 값 자체의 sweep 은
슬라이스 9다. 기대 칸에 "픽스처 상한은 2" 를 적어 두었다.

## `npm run check` 뒤에 재생하면 표가 조용히 달라진다 — 그래서 막았다

**쓰기 도구 확인(`scripts/mcp-write-check.mjs`)은 샌드박스에 정말로 파견하고 착륙한다.** 그 뒤에
재생하면 atlas/slice2 가 머지돼 사라지고(1번 불일치, 4번은 선행이 완료돼 자격이 생겨 불일치)
cobalt 2번이 "이미 돌고 있음" 이 된다(3번 불일치). 2026-09-11 실측으로 **9개 중 6개만 맞아 일치율이
66.7% 로 적혔다** — 판정이 틀린 게 아니라 픽스처가 달라진 것이다.

두 겹으로 막았다:

1. `npm run eval` 이 `npm run fixture` 를 먼저 돈다 (`npm run check` 와 같은 꼴).
2. `scripts/eval.mjs` 가 재생 전에 **픽스처가 정의 그대로인지** 본다 — 프로젝트별 워크스페이스 목록과
   본체 `PLAN.md` 를 `FIXTURE` 정의와 대조하고, 다르면 무엇이 다른지 적고 **exit 2** 로 멈춘다.
   `node scripts/eval.mjs` 를 직접 부른 경우까지 막힌다.

## 두 번 돌려 같은가

같다. 연속 두 번의 결과 파일에서 **판정·개수·격리·사유 문장까지 동일**했다(2026-09-11 실측).

다만 사유 문장 두 곳은 시각을 담는다 — 2번의 `잠듦(claude done 21:59)` 과 6번의 `초기화 02:44` 는
`now` 에서 분 단위로 계산된다. **분이 바뀌는 순간에 걸쳐 돌면 그 문자열만 달라진다**(실측: 09:09 과 09:18
실행에서 `02:44` → `02:53`). 판정(`match`/`mismatch`)과 개수는 영향받지 않는다.
